## Summary

skill-up currently configures mocked MCP responses at the eval level. Every case in the same eval sees the same `mcp.servers[].config_ref`, so authors cannot keep the same MCP server name and tool names while injecting different project states, search results, or error responses per case.

This proposal adds case-level MCP override support. A case may declare `mcp.servers`, and servers are merged by `name` with case-level entries replacing eval-level entries. The MVP focuses on mocked MCP response overrides, preserves existing eval-level behavior, and ensures parallel cases receive isolated mock fixtures.

## Motivation

Issue [#133](https://github.com/alibaba/skill-up/issues/133) describes a common evaluation need: several cases call the same MCP server, such as `project-mgmt`, while each case needs a different project state, search result, or error response.

Today, authors can only configure this at the eval level:

```yaml
mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-mgmt.yaml
```

That makes every case share the `tool_responses` from `project-mgmt.yaml`. To test branches such as "project is open", "project is closed", "project does not exist", and "tool returns an error", authors must either split the suite into multiple eval files or change the server name per case. Both options are noisy:

1. Splitting eval files fragments benchmark and report comparison.
2. Changing server names diverges from the Skill's production MCP setup.
3. A single global fixture cannot cover tool-result-driven branches well.
4. Shared mutable mock state would be risky when cases execute in parallel.

The current code shape reflects this limitation:

- `config.CaseConfig` has no MCP override field.
- `defaultEvaluator.provisionMCPConfig()` uses `sync.Once` and resolves `evalCfg.MCP` once.
- `prepareRuntimeForCase()` creates a runtime per case but reuses a cloned, globally resolved MCP config.
- Mocked MCP server scripts are generated by `internal/mcp` from `tool_responses`, so different cases need different effective MCP configs before `InstallMCP`.

### Goals

1. **Case-level mocked MCP overrides**: let a case specify a different `config_ref` or complete server config for a same-name mocked MCP server.
2. **Explicit merge semantics**: replace whole server entries by `name`; inherit eval-level servers that are not overridden.
3. **Consistent path semantics**: resolve case-level `config_ref` relative to the Skill directory, matching existing eval-level MCP behavior.
4. **Parallel isolation**: compute and install each case's effective MCP config independently so mock responses cannot leak across cases.
5. **Backward compatibility**: evals that only use eval-level `mcp` continue to work unchanged.
6. **Documented and testable behavior**: add focused unit tests, integration/E2E coverage, and writing-guide examples.

### Non-Goals

1. **No mocked fixture format change**: `tool_responses`, `{{params.xxx}}` templates, and existing mocked server behavior remain unchanged.
2. **No conditional response DSL**: this proposal does not add request-argument matching or multi-branch response rules inside a fixture.
3. **No real MCP per-case guarantee in the MVP**: the first implementation only promises mocked MCP overrides; real MCP overrides can be designed separately.
4. **No Agent Engine protocol change**: Claude Code, Codex, Qoder CLI, Qwen Code, and custom agents continue to receive runtime MCP config through `InstallMCP`.
5. **No cross-case stateful mock reuse**: each case installs its mocked server with its own runtime/session instead of sharing one mock server process.

## Proposal

### User Scenario Quick Reference

#### Scenario 1: Same Project MCP, Different Project State per Case

The eval declares the default mocked MCP server:

```yaml
schema_version: v1alpha1

environment:
  type: none

engine:
  name: codex

mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-default.yaml

cases:
  files:
    - cases/project-open.yaml
    - cases/project-closed.yaml
```

The first case overrides the project state to "open":

```yaml
id: project-open
title: Continue the publish plan when the project is open

input:
  prompt: Check project status and continue the publish plan.

mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-open.yaml

judge:
  type: rule_based
  success:
    - output_contains:
        any: ["continue", "publish plan"]
```

The second case overrides the project state to "closed":

```yaml
id: project-closed
title: Stop the publish plan when the project is closed

input:
  prompt: Check project status and decide whether to continue.

mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-closed.yaml

judge:
  type: rule_based
  success:
    - output_contains:
        any: ["stop", "closed", "cannot continue"]
```

Both fixtures define the same tool:

```yaml
tool_responses:
  get_project:
    default:
      id: "p-001"
      status: "OPEN"
```

```yaml
tool_responses:
  get_project:
    default:
      id: "p-001"
      status: "CLOSED"
```

Key points:

- The Skill still sees the MCP server as `project-mgmt`.
- The Skill still calls the tool as `get_project`.
- Only the mocked fixture changes per case.

#### Scenario 2: Override One Server and Inherit the Others

```yaml
# eval.yaml
mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-default.yaml
    - name: filesystem
      mode: mocked
```

```yaml
# cases/project-error.yaml
id: project-error
input:
  prompt: Inspect the project and summarize available files.

mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-error.yaml
```

The effective MCP config is:

```yaml
mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-error.yaml
    - name: filesystem
      mode: mocked
```

### Schema Shape

Add an optional field to `CaseConfig`:

```go
type CaseConfig struct {
    ID               string      `yaml:"id"`
    Title            string      `yaml:"title"`
    Description      string      `yaml:"description"`
    Tag              string      `yaml:"tag"`
    Input            Input       `yaml:"input"`
    Context          Context     `yaml:"context"`
    Constraints      Constraints `yaml:"constraints"`
    Expect           Expect      `yaml:"expect"`
    Judge            JudgeConfig `yaml:"judge,omitempty"`
    MCP              MCPConfig   `yaml:"mcp,omitempty"`
    CollectArtifacts []string    `yaml:"collect_artifacts,omitempty"`
}
```

This proposal chooses `mcp` instead of `mcp_overrides` because:

1. It reuses the existing `MCPConfig` and `MCPServer` structures.
2. Users can copy an eval-level `mcp.servers` entry into a case and adjust only the fixture path.
3. Future support for additional case-level server fields or real MCP overrides would not require another field rename.

The MVP validation rule is intentionally narrow: case-level `mcp.servers` entries must use `mode: mocked`. This keeps the safety and compatibility boundary around fixture variation instead of adding per-case credentials, network policy, or external service differences.

### Merge Semantics

The effective MCP config is calculated as follows:

1. Start with eval-level `mcp.servers`, preserving order.
2. Process each case-level `mcp.servers` entry:
   - If `name` matches an eval-level server, replace that entire server entry.
   - If `name` does not exist at eval level, append the server to the end.
3. Replacement is whole-entry replacement, not deep merge. A case-level override must provide the full server entry it needs, including `name`, `mode`, and `config_ref`.
4. Duplicate server names are invalid within the same level.
5. A case without case-level `mcp` behaves exactly like today and uses the eval-level MCP config.

Whole-entry replacement is easier to review than field-level merging and avoids accidental combinations of eval-level `transport`, `command`, or `endpoint` values with case-level `config_ref` values.

### Runtime Behavior

The evaluator computes each case's effective MCP config while preparing that case's runtime:

```text
caseCfg + evalCfg.MCP
        |
        v
mergeEffectiveMCPConfig(evalMCP, caseMCP)
        |
        v
mcp.Provisioner{SkillDir}.Provision(effectiveMCP)
        |
        v
runtime env + runtime.MCPConfig
        |
        v
ag.InstallMCP(ctx, rt, mcpCfg)
```

The important change is that `provisionMCPConfig()` can no longer rely only on a global `sync.Once` over `evalCfg.MCP` for cases with overrides. For overridden cases, provisioning must happen at case scope so the generated mocked server script embeds the correct fixture.

### Notes/Constraints/Caveats

1. `config_ref` remains relative to the Skill directory, not the case file directory.
2. The MCP server `name` remains stable when a case overrides a same-name server, so the Skill's MCP tool-calling logic does not change.
3. Mocked MCP servers are still generated by `internal/mcp` as local stdio Node scripts; this proposal does not change the MCP protocol layer.
4. Missing fixture files should report the case ID, server name, and original `config_ref`.
5. Re-provisioning identical fixtures for multiple cases is allowed in the initial implementation; simplicity and isolation matter more than a small parsing cache.

### Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Unclear merge semantics | Users may assume field-level deep merge | Document whole-entry replacement and show complete server entries in examples |
| Case-level real MCP expands the scope | Credentials, network, and external service behavior become more complex | MVP validation only permits `mode: mocked` at case level |
| Parallel mock response leakage | Flaky or incorrect evaluations | Compute, provision, and install MCP config per case runtime |
| Existing `sync.Once` cache hides overrides | Case overrides do not take effect | Make MCP provisioning case-aware and keep any eval-only cache as an explicit fast path |
| Poor fixture error messages | Users cannot locate broken case fixtures | Wrap errors with case ID, server name, and `config_ref` |

## Design Details

### Schema Changes

Add this field to `CaseConfig` in `internal/config/schema.go`:

```go
MCP MCPConfig `yaml:"mcp,omitempty"`
```

`MCPConfig` and `MCPServer` do not need new fields. Case YAML can reuse the same shape:

```yaml
mcp:
  servers:
    - name: project-mgmt
      mode: mocked
      config_ref: evals/fixtures/mcp/project-open.yaml
```

`internal/config/loader_test.go` should cover deserializing case-level `mcp`, including `name`, `mode`, and `config_ref`.

### Effective MCP Config Calculation

Add a pure helper, either in `internal/config` or `internal/evaluator`, to merge eval and case MCP config:

```go
func MergeCaseMCP(evalMCP config.MCPConfig, caseMCP config.MCPConfig) (config.MCPConfig, error)
```

Recommended rules:

1. If `caseMCP.Servers` is empty, return a deep copy of eval-level MCP.
2. Build a `name -> index` map for eval-level servers while preserving order.
3. Reject duplicate names within eval-level or case-level servers.
4. For each case-level server:
   - reject empty `name`;
   - require `mode: mocked` for the MVP;
   - replace a same-name eval-level server;
   - append a new name to the end.
5. Return a fresh `MCPConfig` so callers cannot mutate the original config.

Allowing a case to append a new mocked server is useful for cases that need an extra tool without forcing every case in the eval to install that server.

### Evaluator Changes

Current flow:

```go
func (e *defaultEvaluator) prepareRuntimeForCase(...) (runtime.Runtime, error) {
    rtCfg := e.evalCfg.Environment.ToRuntimeConfig()
    mcpCfg, mcpEnv, err := e.provisionMCPConfig()
    ...
    setupCaseEnvironment(..., mcpCfg)
}

func (e *defaultEvaluator) provisionMCPConfig() (...) {
    e.mcpOnce.Do(func() {
        provisioner.Provision(e.evalCfg.MCP)
    })
}
```

Proposed flow:

```go
func (e *defaultEvaluator) prepareRuntimeForCase(
    ctx context.Context,
    caseCfg *config.CaseConfig,
    configName string,
    ag agent.Agent,
) (runtime.Runtime, error) {
    rtCfg := e.evalCfg.Environment.ToRuntimeConfig()
    mcpCfg, mcpEnv, err := e.provisionMCPConfigForCase(caseCfg)
    if err != nil {
        return nil, err
    }
    rtCfg.Env = mergeEnvMaps(rtCfg.Env, mcpEnv)
    ...
}
```

`provisionMCPConfigForCase` should:

1. call `MergeCaseMCP(e.evalCfg.MCP, caseCfg.MCP)`;
2. resolve the effective config with `mcp.Provisioner{SkillDir: skillDir}`;
3. wrap errors with the case ID;
4. return runtime MCP config and env vars required by agent execution.

An eval-only fast path can keep the existing `sync.Once` cache when no case has overrides. The first implementation may also provision per case unconditionally; reading YAML and generating scripts is cheap compared with running an Agent Engine.

### Provisioner and Path Resolution

`internal/mcp.Provisioner` already resolves `config_ref` through `SkillDir`:

```go
func (p Provisioner) resolveConfigRef(configRef string) string {
    if filepath.IsAbs(configRef) || p.SkillDir == "" {
        return filepath.Clean(configRef)
    }
    return filepath.Join(p.SkillDir, configRef)
}
```

This proposal keeps that behavior unchanged for both eval-level and case-level MCP config:

- relative paths resolve from the Skill directory;
- absolute paths are cleaned and used directly.

The writing guides should call this out so users do not assume case-level `config_ref` is relative to the case file directory.

### Parallel Execution Isolation

`prepareRuntimeForCase()` already creates a runtime per case. Case-scoped MCP provisioning and `InstallMCP` are enough to preserve parallel isolation:

1. Case A and case B compute separate effective MCP configs.
2. Case A and case B generate separate mocked MCP Node scripts.
3. Each Agent installs MCP into its own runtime/session.
4. Mock server processes do not share memory or fixture maps.

The implementation should avoid parsing `tool_responses` into a global mutable map shared by multiple cases. The current design embeds fixture JSON into the generated Node script, which is naturally compatible with case isolation.

### Errors and Validation

`ValidateCaseConfig` should validate case-level MCP:

1. `mcp.servers[].name` is required.
2. `mcp.servers[].mode` must be `mocked` in the MVP.
3. Duplicate server names within a case are invalid.
4. Mocked server entries should not declare `transport: http`, `endpoint`, `command`, or `args`; this can be caught by the validator or by reusing existing Provisioner errors.

Provisioning errors should be wrapped with enough context:

```text
case project-open: failed to provision MCP servers: failed to load mcp server "project-mgmt" config_ref evals/fixtures/mcp/project-open.yaml: no such file or directory
```

### Documentation and Templates

Update:

1. `docs/guide/writing-evals.md` with a per-case mocked MCP override example.
2. `docs/zh/guide/writing-evals.md` with the matching Chinese example.
3. `skills/skill-upper/assets/eval.yaml.tmpl` or the relevant reference docs to mention that eval-level MCP is the default and case-level mocked fixtures may override it.
4. Any schema/reference docs that enumerate `CaseConfig` fields.

## Test Plan

### Unit Tests

1. `internal/config/loader_test.go`
   - case YAML with `mcp.servers` loads correctly;
   - missing case-level `mcp` leaves `CaseConfig.MCP.Servers` empty.

2. `internal/config/validator_test.go`
   - case-level mocked MCP is valid;
   - case-level real MCP is rejected in the MVP;
   - missing server `name` is rejected;
   - duplicate case-level server names are rejected.

3. Merge helper tests
   - no case MCP inherits the eval MCP config;
   - same-name servers are replaced as whole entries and order is preserved;
   - new servers are appended;
   - merging does not mutate the original eval or case config.

4. `internal/mcp/provisioner_test.go`
   - case-level `config_ref` resolves relative to SkillDir;
   - two same-name mocked servers with different fixtures produce runtime configs containing different fixture JSON in their generated scripts.

5. `internal/evaluator/evaluator_test.go`
   - a fake agent records each case's `InstallMCP` input;
   - two cases with the same server name and different `config_ref` values receive different runtime MCP configs;
   - `cases.parallelism > 1` does not cross wires between case configs.

## Drawbacks

1. Repeating a complete `mcp.servers` entry in a case is slightly longer than a narrow `mcp_overrides.project-mgmt.config_ref` shape.
2. The MVP does not let users override real MCP endpoints or credentials per case.
3. Provisioning MCP per case may read the same fixture file more than once, though the cost is negligible compared with Agent execution.
4. `config_ref` remains relative to SkillDir rather than the case file directory; this is consistent but needs clear documentation.

## Alternatives

### Alternative A: Add `mcp_overrides`

Example:

```yaml
mcp_overrides:
  project-mgmt:
    config_ref: evals/fixtures/mcp/project-open.yaml
```

This is shorter and fixture-focused. However, it introduces a second MCP configuration shape, requires field-level merge rules, and is less extensible if cases later need to append servers or override more server fields.

### Alternative B: Put All Case Responses in One Fixture

Example:

```yaml
tool_responses:
  get_project:
    cases:
      project-open:
        status: OPEN
      project-closed:
        status: CLOSED
```

This keeps eval-level MCP unchanged, but the mock server would need to know the active case ID. That couples fixtures to the eval runner and makes fixture files grow quickly.

### Alternative C: Require Separate Eval Files

This is possible today, but it duplicates configuration, fragments reports, complicates benchmark comparison, and does not satisfy the issue's request to vary mock responses inside one eval.

### Alternative D: Resolve Case `config_ref` Relative to the Case File

This improves local file ergonomics, but it creates a second path model that differs from existing MCP `config_ref` behavior. This proposal keeps the current SkillDir-relative rule.

## Infrastructure Needed

No new services or third-party dependencies are required.

Implementation only needs Go code changes, test fixtures, docs, and skill template/reference updates. Mocked MCP continues to use the existing Node stdio mock server generation.

## Upgrade & Migration Strategy

This change is backward compatible:

1. Existing eval-level `mcp` config continues to work.
2. Existing case files do not need new fields.
3. Cases without case-level `mcp` behave exactly as they do today.
4. Users can gradually migrate only the cases that need fixture variation.

Documentation should clearly state:

- case-level MCP overrides are introduced by SUP-0003;
- the MVP supports mocked MCP overrides;
- real MCP per-case overrides require a separate design discussion covering security, network, and credential boundaries.
